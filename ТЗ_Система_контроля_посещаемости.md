# Техническое задание
## Система контроля посещаемости и успеваемости студентов ДВФУ

### 1. Общие положения

#### 1.1. Назначение документа

Настоящее техническое задание (ТЗ) определяет требования и порядок разработки системы контроля посещаемости и успеваемости студентов ДВФУ.

#### 1.2. Основание для разработки

Основанием для разработки системы является потребность ДВФУ в автоматизации процессов учета и контроля посещаемости студентами занятий и их успеваемости по изучаемым дисциплинам.

#### 1.3. Плановые сроки начала и окончания работ

Начало работ: с момента утверждения ТЗ.
Окончание работ: через 10 часов с момента начала работ.

#### 1.4. Порядок оформления и предъявления результатов

Результаты работ предоставляются в виде рабочей версии системы контроля посещаемости и успеваемости с полным функционалом, описанным в данном ТЗ. Работы считаются выполненными после проверки всех функций системы согласно требованиям и подписания акта приемки-сдачи работ.

### 2. Назначение и цели создания системы

#### 2.1. Назначение системы

Система предназначена для автоматизации учета посещаемости и успеваемости студентов ДВФУ. Система позволяет преподавателям отмечать присутствие студентов на занятиях, выставлять оценки за выполненные работы, а администрации университета – получать аналитические данные о посещаемости и успеваемости как отдельных студентов, так и групп.

#### 2.2. Цели создания системы

1. Повышение эффективности учета посещаемости студентами учебных занятий
2. Создание единой среды для контроля успеваемости студентов
3. Автоматизация процесса анализа учебной активности студентов
4. Обеспечение прозрачности процесса оценивания для всех участников образовательного процесса
5. Оптимизация работы преподавателей при учете посещаемости и выставлении оценок

### 3. Модель предметной области

#### 3.1. Описание предметной области

Предметная область охватывает образовательный процесс в ДВФУ, включающий в себя:
- Кафедры как основные структурные подразделения
- Учебные группы, состоящие из студентов
- Преподавателей, отвечающих за определенные дисциплины
- Дисциплины с расписанием занятий различных типов (лекции, семинары, практические занятия)
- Учет посещаемости студентами занятий
- Учет успеваемости студентов (выполнение заданий, сдача тестов, экзаменов)
- Систему формирования отчетов о посещаемости и успеваемости

### 4. Требования к системе

#### 4.1. Требования к системе в целом

##### 4.1.1. Требования к структуре и функционированию

Система должна иметь следующую структуру:
1. Подсистема авторизации и аутентификации
2. Подсистема управления пользователями
3. Подсистема управления учебными группами
4. Подсистема управления дисциплинами и расписанием
5. Подсистема контроля посещаемости
6. Подсистема контроля успеваемости
7. Подсистема формирования отчетов
8. Подсистема администрирования

##### 4.1.2. Требования к персоналу

Для работы с системой пользователям не требуется специальных технических навыков, кроме базовых навыков работы с веб-браузером.

##### 4.1.3. Требования к надежности

1. Система должна быть доступна 24/7 с плановыми техническими перерывами не более 2 часов в месяц.
2. Среднее время восстановления после сбоя не должно превышать 1 час.
3. Данные должны сохраняться при любых сбоях системы.

##### 4.1.4. Требования к безопасности

1. Все данные пользователей должны храниться в зашифрованном виде.
2. Доступ к системе должен осуществляться только по защищенному протоколу HTTPS.
3. Пароли пользователей должны храниться в виде хешей с использованием современных алгоритмов хеширования (bcrypt).
4. Система должна быть защищена от основных типов атак (SQL-инъекции, XSS, CSRF).
5. Все действия администраторов должны логироваться.
6. Оценки и данные о посещаемости должны быть защищены от несанкционированных изменений.

#### 4.2. Требования к функциям, выполняемым системой

##### 4.2.1. Подсистема авторизации и аутентификации

Функции:
1. Регистрация новых пользователей с указанием роли
2. Авторизация существующих пользователей
3. Восстановление забытого пароля
4. Поддержание сессии пользователя
5. Выход из системы

##### 4.2.2. Подсистема управления пользователями

Функции:
1. Создание, редактирование и удаление пользователей (для администратора)
2. Назначение ролей пользователям (для администратора)
3. Назначение заведующих кафедрами (для администратора)
4. Привязка студентов к учебным группам
5. Редактирование профиля пользователя

##### 4.2.3. Подсистема управления учебными группами

Функции:
1. Создание, редактирование и удаление учебных групп (для зав. кафедрой)
2. Добавление и удаление студентов из групп (для зав. кафедрой)
3. Просмотр состава групп
4. Просмотр успеваемости и посещаемости по группам

##### 4.2.4. Подсистема управления дисциплинами и расписанием

Функции:
1. Создание, редактирование и удаление дисциплин (для зав. кафедрой)
2. Назначение преподавателя на дисциплину (для зав. кафедрой)
3. Создание расписания занятий для дисциплины
4. Просмотр расписания занятий

##### 4.2.5. Подсистема контроля посещаемости

Функции:
1. Отметка присутствия/отсутствия студентов на занятиях (для преподавателя)
2. Указание причины отсутствия (уважительная/неуважительная)
3. Просмотр статистики посещаемости
4. Автоматическое формирование отчетов о посещаемости

##### 4.2.6. Подсистема контроля успеваемости

Функции:
1. Создание заданий и контрольных точек в рамках дисциплины
2. Выставление оценок за выполненные задания
3. Выставление итоговых оценок по дисциплине
4. Просмотр текущей успеваемости студентом

##### 4.2.7. Подсистема формирования отчетов

Функции:
1. Формирование отчетов о посещаемости (по студентам, группам, дисциплинам)
2. Формирование отчетов об успеваемости (по студентам, группам, дисциплинам)
3. Экспорт отчетов в различные форматы (PDF, Excel)
4. Настройка параметров отчетов

##### 4.2.8. Подсистема администрирования

Функции:
1. Мониторинг активности пользователей
2. Управление кафедрами
3. Просмотр статистики использования системы
4. Управление настройками системы
5. Настройка типов оценок и шкал оценивания

#### 4.3. Требования к видам обеспечения

##### 4.3.1. Требования к информационному обеспечению

1. Основным хранилищем данных должна быть реляционная база данных.
2. Структура базы данных должна обеспечивать целостность и непротиворечивость данных.
3. База данных должна регулярно резервироваться.
4. Должна быть обеспечена возможность восстановления данных из резервных копий.

##### 4.3.2. Требования к программному обеспечению

1. Система должна функционировать в виде веб-приложения.
2. Интерфейс пользователя должен быть реализован с использованием современных веб-технологий.
3. Система должна быть совместима с основными современными браузерами (Chrome, Firefox, Safari, Edge).
4. Система должна корректно работать на мобильных устройствах.

##### 4.3.3. Требования к техническому обеспечению

1. Сервер должен обеспечивать обработку не менее 1000 одновременных пользователей.
2. Время отклика системы не должно превышать 2 секунды при нормальной нагрузке.
3. Система должна быть масштабируемой для увеличения производительности при росте нагрузки.

### 5. Требования к интерфейсу пользователя

#### 5.1. Страницы системы

В системе должны присутствовать следующие страницы:
1. Страница авторизации
2. Страница регистрации
3. Домашняя страница для разных ролей пользователей
4. Страница управления учебными группами
5. Страница управления дисциплинами
6. Страница учета посещаемости занятий
7. Страница учета успеваемости
8. Страница просмотра статистики и отчетов
9. Страница управления пользователями

#### 5.2. Регистрация пользователей

Страница регистрации должна содержать форму со следующими полями:
1. Имя (обязательное поле)
2. Фамилия (обязательное поле)
3. Email (обязательное поле)
4. Учебная группа (обязательное поле для роли студент, выбор из списка)
5. Пароль (обязательное поле)
6. Фотография (необязательное поле, допустимые форматы: jpg, jpeg, png, размером не больше 2Мб)

#### 5.3. Авторизация пользователей

Для авторизации пользователи должны использовать email и пароль, указанные при регистрации.

#### 5.4. Специфические интерфейсные требования

##### 5.4.1. Требования для разных ролей

1. Зав. кафедрой может:
   - Формировать перечень учебных групп и изучаемых ими дисциплин
   - Назначать ответственного преподавателя за дисциплину
   - Просматривать статистику посещаемости и успеваемости по кафедре
   - Формировать отчеты о работе кафедры

2. Преподаватель может:
   - Просматривать закрепленные за ним дисциплины и группы
   - Отмечать посещаемость студентов на занятиях
   - Создавать контрольные точки и выставлять оценки
   - Просматривать статистику посещаемости и успеваемости своих студентов

3. Студент может:
   - Просматривать свое расписание занятий
   - Видеть свою посещаемость и успеваемость
   - Получать уведомления о новых оценках и пропусках

4. Администратор может:
   - Формировать список кафедр учебного заведения
   - Назначать зав. кафедрой
   - Управлять системными настройками
   - Иметь доступ ко всем отчетам системы

### 6. Сценарии использования

#### 6.1. Отметка посещаемости

1. Преподаватель авторизуется в системе
2. Переходит на страницу учета посещаемости
3. Выбирает дисциплину, группу и дату занятия
4. Отмечает присутствующих/отсутствующих студентов
5. Для отсутствующих указывает причину (при наличии)
6. Сохраняет информацию в системе

#### 6.2. Выставление оценок

1. Преподаватель авторизуется в системе
2. Переходит на страницу учета успеваемости
3. Выбирает дисциплину, группу и контрольную точку
4. Выставляет оценки студентам
5. Может оставить комментарий к оценке
6. Сохраняет информацию в системе

#### 6.3. Просмотр успеваемости студентом

1. Студент авторизуется в системе
2. На домашней странице видит сводную информацию о своей успеваемости
3. Может перейти на детальную страницу успеваемости по конкретной дисциплине
4. Видит все свои оценки, средний балл и комментарии преподавателей

#### 6.4. Формирование отчета о посещаемости

1. Зав. кафедрой авторизуется в системе
2. Переходит на страницу отчетов
3. Выбирает тип отчета "Посещаемость"
4. Указывает параметры отчета (период, группа, дисциплина)
5. Система формирует отчет с визуализацией данных
6. Зав. кафедрой может экспортировать отчет в PDF или Excel

### 7. Требования к производительности системы

#### 7.1. Frontend производительность

1. Время загрузки страниц не должно превышать 1.5 секунды при хорошем интернет-соединении
2. Интерфейс должен быть отзывчивым и работать без заметных задержек
3. Отметка посещаемости должна быть оптимизирована для быстрого ввода данных

#### 7.2. Backend производительность

1. Время ответа сервера не должно превышать 0.5 секунды для 95% запросов
2. Система должна обрабатывать не менее 100 запросов в секунду
3. Максимальное время формирования сложных отчетов не должно превышать 10 секунд

### 8. Требования к информационной безопасности

1. Аутентификация пользователей должна осуществляться через безопасный механизм с использованием JWT токенов
2. Все данные должны передаваться по защищенному протоколу HTTPS
3. Пароли должны храниться в хешированном виде
4. Система должна быть защищена от распространенных уязвимостей (SQL-инъекции, XSS, CSRF)
5. Должно вестись логирование всех изменений оценок и посещаемости с указанием автора изменений

### 9. Требования к доступности для людей с ограниченными возможностями

1. Интерфейс должен соответствовать стандарту WCAG 2.1 уровня AA
2. Должна поддерживаться навигация с помощью клавиатуры
3. Все элементы интерфейса должны иметь достаточный контраст
4. Необходимо предусмотреть альтернативные текстовые описания для всех графических элементов

### 10. Требования к взаимодействию компонентов системы

1. Компоненты системы должны взаимодействовать через API
2. API должно быть документировано
3. Должен быть реализован механизм кэширования для повышения производительности
4. Компоненты должны быть слабо связаны для обеспечения масштабируемости

### 11. Требования к фреймворкам и языкам программирования

#### 11.1. Frontend

1. Фреймворк: React.js или Vue.js последней стабильной версии
2. JavaScript: ES6+ или TypeScript
3. CSS: использование современных подходов (Flexbox, Grid)
4. Адаптивный дизайн с использованием подхода Mobile First

#### 11.2. Backend

1. Язык программирования: Python 3.8+ или Node.js 14+
2. Фреймворк: Django/Flask (для Python) или Express.js (для Node.js)
3. ORM: SQLAlchemy (для Python) или Sequelize (для Node.js)
4. Система управления базами данных: PostgreSQL 12+

### 12. Требования к графическому оформлению

1. Дизайн должен соответствовать корпоративному стилю ДВФУ
2. Интерфейс должен быть интуитивно понятным и современным
3. Цветовая схема: основные цвета ДВФУ (синий, белый) с дополнительными акцентными цветами
4. Шрифты: системные шрифты или Google Fonts с хорошей читаемостью
5. Для визуализации статистики должны использоваться наглядные графики и диаграммы

### 13. Требования к аппаратно-техническому обеспечению

#### 13.1. Серверная часть

1. CPU: не менее 4 ядер
2. RAM: не менее 8 ГБ
3. Дисковое пространство: не менее 100 ГБ (SSD)
4. Сетевое подключение: не менее 100 Мбит/с

#### 13.2. Клиентская часть

1. Современный веб-браузер (Chrome 88+, Firefox 85+, Safari 14+, Edge 88+)
2. Доступ в интернет со скоростью не менее 5 Мбит/с
3. Устройство с разрешением экрана не менее 320px по ширине

### 14. Требования к срокам выполнения

1. Верстка и дизайн: 4 часа
2. Программирование серверной и клиентской части: 6 часов
3. Общий срок разработки: 10 часов
